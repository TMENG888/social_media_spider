微信视频号三机 Redis 分布式采集——生产运行操作流程

一、部署前

1. 在同一局域网内选择一台稳定设备运行 Redis 6.2+，启用密码和持久化（建议 AOF），只向可信局域网开放 6379。
2. 三台采集机器分别复制完整的“视频号”生产目录，不复制其他机器历史 .state、runs、logs。
3. 三台机器安装并登录 PC 微信，保持微信前台可操作，关闭会遮挡微信的悬浮窗口。
4. 分辨率选择 2560x1440 或 1920x1080，Windows 缩放使用 100% 或 150%。
5. 三台机器使用相同 REDIS_URL、REDIS_PASSWORD、REDIS_RUN_ID；每台机器使用不同 worker-01/02/03 启动器。Redis密码已分别保存在 worker-01/02/03\.credentials\redis-password.txt，公共启动脚本会自动读取，正常启动时不再询问Redis密码。该文件属于敏感明文凭据，只能部署到受信任设备。
6. 配置相同的 MySQL 地址、数据库、用户名和密码。启动器会先执行环境检查和数据库连通性检查。

二、启动

机器1双击：worker-01\启动Redis动态工作节点.bat
机器2双击：worker-02\启动Redis动态工作节点.bat
机器3双击：worker-03\启动Redis动态工作节点.bat

Redis任务分发机另执行：powershell -ExecutionPolicy Bypass -File common\start-central-log-sink.ps1
该接收器不执行采集，只把三台节点回传到Redis的脱敏日志持续保存到central-logs目录；关闭后再次启动会从原子游标续收。

三、任务如何分配

1. common\task-queue.json 被展平为 276 个“专题+单关键词”任务。
2. 相同 REDIS_RUN_ID 只播种一次；三台机器通过 Redis Streams consumer group 动态领取任务。
3. 节点空闲后立即领取下一关键词，速度快的机器会自动承担更多任务，不受静态 93/92/91 数量限制。
   三台 worker 默认均为 mixed：都能领取不同的主关键词，也都能处理精准视频补采；Redis 租约保证同一关键词同一时刻只归一个节点。
4. 每 30 秒续租一次；连续 3 次心跳失败会在当前视频结束后安全停止。失联任务 300 秒后可由其他机器接管。
5. 节点启动后先尝试回收至多1个已静默超过300秒的旧主任务pending；完成这一次有界复查后立即回到未读新关键词，避免旧异常无限循环，也避免长期饿死旧断点。

四、单个关键词的实际采集流程

1. 从 Redis 和本机 SQLite 恢复视频级检查点、完整文章行、评论、字段完成度、重试与死信状态。
2. 打开“搜一搜 > 视频 > 最新”，回到列表顶部，按最新到最旧滚动。
3. 每张卡片先计算“标题+作者+时长”指纹：
   - 已完成：只读卡片并跳过，不打开详情。
   - retry_pending：打开详情，精准重试该视频。
   - 新视频：正常打开详情采集。
   - dead_letter：只读卡片并跳过，保留死信审计。
4. 正常记录优先以 finder id 作为文章id；没有 finder id 时使用标题、作者、发布时间、时长复合键。
5. 专题一采集视频文章；专题二同时采集页面实际公开评论。
6. 到达 2026-01-01 之前的第一条视频或确认列表耗尽后，结束该关键词。

五、失败和断点

1. 一个关键词一轮只扫描一次；一条视频一轮只尝试一次，不再立即把整个关键词从头重跑 5 轮。
2. 失败视频写入 video_checkpoint=retry_pending，保存指纹、索引、标题、作者、错误和截图；年度主扫描结束时将其原子去重写入独立 video-retry 流，主关键词不再反复整轮重跑。
3. 后续重启或 Redis 回收任务时，从顶部快速读取卡片；已完成视频不打开，仅异常视频重新进入详情。
4. 同一视频跨运行累计第 3 次失败后进入 video_dead_letter；输出 channels_video_dead_letter.csv/jsonl，供人工复核。死信不会无限阻塞其余年度任务。
5. 已提交SQLite记录会在异常后重新导出；MySQL按链接、平台、项目幂等更新，并使用非空字段合并。

六、首次详情一体化采集与异步ASR

1. 新视频第一次打开详情时，同时启动完整音频录制，并在录音期间读取元数据、互动量；专题二还会打开评论面板采集公开评论。
2. 优先使用分享页媒体、微信媒体缓存等可验证的完整媒体；无法取得完整媒体时，按 WeChatAppEx.exe PID 做 Windows 进程回环录音。录音前先做3秒有效波形预检，再从0秒完整录制。
3. 录音结束后立即将完整行、评论、音频任务和视频检查点写入SQLite及Redis，然后关闭详情页；RPA无需等待转写，可继续下一条视频。
4. 每台机器只启动一个常驻 large-v3 服务。后台线程连续消费本机持久化 asr_job，成功后回填“文章视频内容”，并把视频检查点更新为completed。
5. 静音、录音不完整、视频定位失败、转写失败或质量不合格才进入独立video-retry精准补采；正常完成的视频后续只核对卡片指纹，不再二次打开。
6. 关键词年度列表可在异常子视频已持久化后释放主扫描租约，但父关键词保持completed_with_deferred_retries；存在死信时为completed_with_dead_letters。只有全部子视频终态且无死信时才是completed。
7. 新机器接管时若无法读取故障机器本地WAV，会根据Redis中的文章键、指纹和原索引重新定位并只补该视频。

七、完成和入库

1. 年度主扫描到达截止日期或真实列表末尾，且所有未完成视频均已持久化到 video-retry 后，主关键词执行XACK；补采任务只有对应指纹达到完成/无内容/死信终态后才单独XACK。
2. NULL字段不会覆盖MySQL已有有效字段；整批入库失败会回滚。
3. JSON、JSONL、CSV和状态文件均先写临时文件再原子替换，避免断电留下半个文件。

八、停机与续爬

1. 正常停机双击对应 worker 的“安全停止当前任务.bat”。
   脚本会原子写入带时间和worker编号的停止标记；当前视频完成后依次保存SQLite/Redis检查点、导出、入库并退出，不再领取下一任务。停止生命周期会回传集中日志，集中日志接收器不会随worker停止。
2. 不要删除 worker\.state、runs、logs，也不要清空 Redis。
3. 原任务续爬继续使用相同 REDIS_RUN_ID；真正新一轮全量重跑才更换 REDIS_RUN_ID。
4. 每日日志位于 worker-0N\logs；关键词结果和死信表位于 worker-0N\runs\专题\关键词。
5. 分发机集中日志位于central-logs\<REDIS_RUN_ID>\<日期>：all.log/all.jsonl汇总全部节点，另有按consumer拆分的LOG/JSONL。Redis中只保留近似20万条日志事件，密码在XADD前脱敏；集中日志异常不会中断采集。
2026-10-01更新：三台worker默认全部为mixed。新视频首次详情访问即一体化采集元数据、互动量、专题二评论和完整音频；录音结束即保存检查点，常驻large-v3在后台转写，RPA继续下一条。video-retry仅处理静音、录音不完整、定位失败、ASR失败或质量不合格的视频，不再把正常视频重新打开。

2026-09-29重置保障：中央Redis run命名空间首次启动时生成generation。worker的SQLite、截图和runs结果按Run ID + generation隔离；因此重置中央任务后即使其他机器仍保留上一轮本地文件，新一轮也会从空断点开始，不会沿用旧completed状态。

2026-09-30节奏控制：三台机器分别执行本机随机抖动，同时在每次提交或重建搜一搜关键词前竞争同一个Redis原子令牌；默认跨机器搜索间隔12～25秒。令牌只限制搜索提交，详情采集、播放录音、离线ASR、清洗和入库不会等待该令牌。日志事件为rpa_jitter_pause、redis_search_token_wait、redis_search_token_acquired。
